# 维护制作工作包

## 修改单位

一次新增能力同时更新工具帮助、schema/示例、对应Skill、失败诊断和能力状态。只加入提示词不宣称能力已成立；只跑通文件转换也不宣称艺术结果已验证。

公共代码与知识以当前仓库为源。作品、模型缓存、游戏本体和私有素材留在独立目录；不从已安装的游戏目录打包整个profile。

## 验证顺序

1. 对新能力跑真实的小输入和一个有意义的失败案例；保护冻结输入与明确差异。
2. 运行受影响测试，然后运行已有集成链，检查缓存/恢复与交付合同。
3. 执行`bundle-check`检查公共包引用、Skill与必要文件；解包到干净目录从START_HERE开始。
4. 游戏/音频/艺术验收单独记录。CI不能运行的部分标明未验证；保存用户实际听看的版本。

```shell
python run_pipeline.py bundle-check
python -m unittest discover -s tests -v
```

独立冷启动评测只给公共包、brief与必要原始输入，评测agent不继承开发对话和标准修复答案。它应能定位一个故意错误、修订候选、生成可听看产物并写正确交接。记录人工介入、返工、耗时与费用。

## Skill维护

八个项目Skill位于`skills/`，采用标准Markdown入口，不依赖宿主私有工具。入口只保留职责、必要约束和路由；详细教程在各自`references/guide.md`，大文件与历史资料按需读取。

新增或修改Skill要检查YAML frontmatter、相对链接、命令是否真实存在、例子是否可执行、完成条件是否可检查。Skill解释专业选择，工具实施精确操作；保留用户明确目标，不把一个案例的色彩/BPM/布局写成普遍要求。

## 上游参考更新

固定快照位于`skills/_upstream/minecraft-agent-skills`，含原始MIT LICENSE、四份`.txt`和`provenance.json`。`.txt`是参考资料，不是自动启用的Skill。更新时固定新commit、验证许可证与SHA256，审查目标版本差异；不要直接把上游AGENTS覆盖本项目。

上游案例主要覆盖更广的Minecraft版本，包内项目Skill负责选择本项目1.21.1适用路线。完整构建和实际游戏验证仍需运行。外部资料有许可变化时保留旧锁与替代路线，不悄悄改用latest。

## 发布

源码包包括入口、Skill/教程、工具、schema、原创样例、客户端源码、profile与第三方说明。wheel、源码ZIP和运行包各自验证包含内容；源码包不混入作品、凭据、Minecraft资产或未核实授权的大文件。

记录release版本、source commit、测试范围、真实游戏版本和未验证项。已发布的源码不等于作品已录制、投稿或获得艺术认可。原始记录与旧可用版本保留，迁移有明确schema与回退步骤。
