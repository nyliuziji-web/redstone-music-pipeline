# 从需求到交付

默认agent自主推进，在代表样段和最终成品时请用户听看。先确认仍会改变作品方向的缺失信息，常规实现与修复继续工作。

## 保留两种音乐和五类证据

音乐母版表达用户想要的音乐，游戏改编表达音符盒能执行的选择。原始输入与已认可文件冻结hash；局部修改生成新候选，记录源音符去向和取舍。

证据分为静态文件、真实服务端、实际客户端、艺术反馈、录制成片。某一层通过不能提升另一层状态；用户反馈绑定具体文件/世界、hash、片段和范围。

## 阶段门

| 阶段 | agent的判断 | 主要产物与退出条件 |
|---|---|---|
| 需求与体检 | 哪个版本、完整还是节选、缺什么、先听看什么 | brief、输入清单、环境能力；真实素材可读且范围明确 |
| 音乐母版 | 主题、低音、和声、节奏、段落各承担什么 | 全曲结构与角色、MIDI、GM试听；不同风险段已有对照 |
| 游戏编配与声音 | 音域/音色、持续策略、共用槽与空间关系 | 适配计划、事件、profile、采样试听；改编损失明确，代表段用户听审 |
| 实体样机 | 时序、复音、加载、相机和停止重播是否可靠 | 可玩世界/投影、真实触发与客户端证据 |
| 全曲 | 样机规则能否承担全曲密度和尾段 | 全曲构建、独立回读、完整播放；不拿短段证明全曲 |
| 视觉和场景 | 主读、细节、留白、声部身份和段落发展 | 模块与效果库、演出数据、机位预览/实录；不破坏机器 |
| 最终听看 | 当前版本是否达到作品目标 | 用户结论与遗留项；修改受影响层后复核 |
| 录制与交付 | 实录音源、编码负载、操作和来源是否清楚 | 成片检查、安装与使用手册、manifest/hash；未投稿就写未投稿 |

选择样段要覆盖主唱或主旋律、长音、密集高潮、角色交接、休止与结尾。可以一次合并数段供用户比较，不把每个音符都变成请示。

## 变更与恢复

先读取`project.json`、`state.json`和最新任务，再运行`status`/`handoff`。`state.json`由工具管理，agent通过任务结果和正式接口提交变更。

- 改MIDI/tempo：声音、机器、视觉和相关证据重建。
- 改声音样本/profile：声音/游戏录音/相关可听认可失效；旋律母版认可可保留。
- 改机器布局：事件坐标、相机、空间混音和场景保护区重验。
- 只改粒子：音乐和实体事件应完全相同；画面/性能/清理重验。

遇到同因失败两次，保留最小复现，改用有理由的路线。创作先比较少量候选，默认两轮修订；用实际差异与反馈决定是否继续，不无限改变风格。

## 决策与交接

```shell
python run_pipeline.py decision projects/my-song --summary "给主旋律分配独立采样槽" --reason "与pad共用事件，调低pad时主题也变小；同增益独奏确认。"
python run_pipeline.py handoff projects/my-song
```

交接应包含最新认可输入、正在解决的问题、实际已验证范围、下一条操作和失败路线。保存简洁决定与证据，不写无法检查的长篇思维过程。

## 学习顺序

先运行原创学习素材，读当前Skill完成一次成功与故意失败练习，再处理用户曲目。现成可信MIDI可以跳过转写，仍需完成声音适配和移动听感。用户提供的素材不足以还原某声部时，明确标注新增编配。
