# 制作判断与复查

按当前遇到的问题选一个修法。先写要听见或看见的变化，每轮只动能验证该变化的一组因素。使用[代表段记录](../templates/sample-review.md)留下基线、修改和复查结果，接手者应能据此继续做。

## 1. 先确定问题出在哪一层

| 看到或听到的问题 | 先做的检查与决定 | 修后证据 |
|---|---|---|
| 谱看起来完整，听上去却不对 | 先看原录音到最后一乐句与 MIDI 末音之间差了什么。抽主题、重复段和结尾。结尾差几秒可能是录音尾巴，也可能缺了结句 | 用 `audio compare` 分别比较靠前与靠尾的同时间切片，打开 `comparison.json` 看最后音及剩余区间，再听是否漏句 |
| 和声整片偏掉，节奏位置却对 | 用一颗已知 C 或主音验算脚本。MIDI 60 的音级是 C，MIDI 30 的音级是 F♯。音级编号加一个非 C 基数会把整个和声平移。查看谱面、bass 音级与实际对应 | 回读首个和弦与低音上的根音；再比较几个远隔的和声。色度相关改善只证明整体音级分布更接近 |
| 错拍或段落标记越到后面越夸张 | 区分音频采样、分析帧、秒、MIDI 增量 tick、游戏局部 GT。传帧边界前检查帧数与 hop length。写 MIDI 时每轨按绝对 tick 排序，写入 `time=当前 tick - 上一个 tick` | `inspect-source` 核对头、中、尾。游戏量化用绝对秒到 20 Hz 一次取整。乐句短句可能为抢拍，不能把全部微时差硬拉成同一网格 |
| 原奏旋律易辨，游戏版连续换音色 | 看 `arrangement-report.json` 的 slot 与原始音高，先找音域触边或整角色移调。优先整声部固定槽，音域确需分区时在有音乐依据的乐句边界处理 | 试听轮廓与接缝，低、中、高音各测一次。把有意移调记在游戏演奏谱里，音乐母版继续保存原来的音区 |
| 起音对但长音掉光，或者结尾糊成一片 | 依次核对母版的收键、声音样本长度、实际调音后的包络和补触发。高音变速后尾巴更短，低音可能覆盖下一个和弦。延音靠音体和触发策略处理 | 先独奏低、中、高音，再听和声转换与终止。在密集段记录补触发和同刻峰值，防止只让独奏更顺耳 |

WorkBuddy 早期《烟袋斜街》回放匹配了 1,852 个实体事件。旧 MIDI 的所有有效 note-on 力度都是 78，旋律在两种音色间切换。旧谱末音约 209.4 秒，录音约 213.6 秒，应专门对照尾段，判断缺音还是自然衰减。统一力度和换色是复查位置的线索。这次服务器通过只能确认实体演奏了所提交的事件。给新 Codex 的任务写明选段、预期声部、音色一致性及听审要求。有不同类型素材时先按[谱面与片段重建](SCORE_FROM_REFERENCES.md)选择证据路线。

## 2. 音色意见先拆成可比较的变量

**Nevada 的主奏太轻。** 当时主题和底色共用 flute。提高整个槽会同时改变背景。实际改为主唱与回声使用独立的 xylophone/骨块槽，底色保留原槽，再对已经认可的候选只提高主奏层。+3 dB 是那一次试听选择，复用的是先隔离槽、再做单变量比较的方法。

- 同一个槽只换采样或增益时，保留事件轨作对照，检查新采样的根音和包络，再实录。
- 拆槽时检查 role → slot → 声音事件 → 方块基座 → 实体 instrument/note。复位后也走同一映射。只换资源包而没有改基座，音符盒仍会按旧乐器触发。
- 比较根音固定的低、中、高三个音。单次播放包络与轨上 MIDI 时值可以不同。判断长音时同时覆盖连音、和声变化和结句。

**《烟袋斜街》的背景不够细。** 从已经认可的编曲出发，先区分“单音内部的细碎泛音”与“独立出现在拍缝或句尾的颗粒”。前者可烘进一个短样本，后者才占新的实体事件。案例保留了基线 238 个事件和相应采样，增加 19 个底色、13 个回声、24 个刷声起音，峰值仍是同刻 5 个。对照是同机位、同增益的基线、全混合、新增层独奏三份。在这次实录中，新增层的 RMS 比基线低约 19 dB，整段混合只高约 0.07 dB。数值说明新增层很轻，是否增加流动感由听审判断。

## 3. 检查「只改一处」是否真的成立

做[原创织体练习](../examples/texture-study/README.md)。两份触发谱可以这样核对：

```shell
python run_pipeline.py texture-study work/texture-review
python examples/production-review/compare_events.py work/texture-review/base/preview-events/events.json work/texture-review/layered/preview-events/events.json > work/texture-review/event-diff.json
```

打开 `event-diff.json`。本例应保留 **80** 个，`missingFromCandidate.total` 为 **0**，新增 **26** 个，峰值仍是 **4**。报告保留重复事件的数量，按局部 GT、声部、音高、乐器、槽与增益代理等字段比较。乐谱重导出可能改写音符 ID，因此工具按实际事件字段比较。一次音高或时刻修改会出现一笔旧事件消失和一笔新事件出现。

真实项目可以比较两份声音阶段的 `events.json`，或比较两份机器阶段的 `expected_events.json`（后者也核对坐标）。两份先对齐同一时间范围。要核实“原声音没变”，还要检查原有槽对应的样本字节、profile 与声音定义。要核实“用户实际听来相同”，再在同一机位、同一设置做客户端试听。静态事件一致也无法证明尾音和空间比例一致。

## 4. 世界静态检查通过后，看完整的移动镜头

《灯巷》有两个不同层的问题。服务端第一次在特定刻发现 X 偏半格，因为 Minecraft 将整数形式的水平坐标自动居中。生成命令改用显式小数后逐音坐标一致。原版客户端也收到了预期的取景角。实际观看反馈仍指出镜头逐句转向显得摇晃。后来将固定朝向、俯仰与缓慢平移确立为默认。

| 遇到的现象 | 应检查的文件或实际操作 |
|---|---|
| 第二段塞不进轨道，或某个近景构件危险 | 先检查上一段尚存的纵向空间，再画两段的共同截面。按[轨道教程](PHRASE_TO_WORLD.md)交错摆位。建筑以完整模块对净空检查，装饰冲突时移动或调整整榀 |
| 匀速前进时画面像点头或不断找方向 | 检查实际连续镜头和配置里的 `yaw/pitch`，先统一方向。以开合、近远层次和静态灯具表达段落，必要时只调平移与高度。坐标检查用于排错，最后看原版连续播放 |
| 用户说画面太暗，休止时只剩空洞 | 在没有特效的休止处先看轮廓。Nevada 在视线附近用固定灯座、肋架和铜边补出结构，再用分段变化。至少比较一对相同机位的亮暗版。亮度还受光影、材质和曝光影响 |
| 测试看得顺，录屏却卡或没声 | 验证有编码器负载时的同段连拍。Nevada 的全曲帧时间记录没有同时录屏，只证明当时独立客户端。每轮先检查声音轨确实录到游戏输出 |

依次做开始、播放中停止、复位、再次开始、保存重开。记录测试究竟在服务端还是带视听的客户端。核对恢复后的基座、事件、资源包和视角。当用户只认可轨道，且给了镜头修改意见，交接要写成两个状态。

## 5. 接手时用实际产物定位，避免接到旧稿

- 用 `status` 读 `state.json` 的阶段指针，发布路径用当轮输出的 `releasePath`。哈希目录按名称排列不能说明哪个较新。播放前确认世界里的包和说明对应这个版本。
- 安装前打开目标实例，确认它使用的 `saves` 目录。启动器可能采用版本隔离，写进全局目录后列表仍不会出现。使用新目录复制世界，保留先前认可的存档。
- 碰到 Windows 的暂存或状态文件替换错误，先保留日志，关闭正在读该文件的程序，重跑原命令。已有阶段可以接续。独立试听要用新输出路径。同名的试听报告仍在时，工具也可能拒绝写入，即使原音频文件已移走。
- 交接只给当前任务需要的输入、样段决定、可玩版本、复查状态和下一条具体操作。结尾执行 `handoff`。制作标准依实际问题采用，历史曲目的槽位、增益、材质、机位与时间不直接套到新曲。
